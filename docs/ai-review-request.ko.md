# ssealed 개선 검토 요청

첨부한 압축 파일은 `ssealed`의 소스 스냅샷이다. 전체 코드를 읽고, 실제 사용과 출시를 앞당기려면 무엇부터 개선해야 하는지 검토해줘. 기존 구현을 당연한 전제로 받아들이지 말고, 복잡한 구조를 유지할 이유가 약하면 더 단순한 대안도 제안해줘.

문제를 억지로 많이 만들지는 마. 파일을 나누거나 테스트를 늘리는 것 자체는 목표가 아니다. 사용자 데이터 보존, CLI 사용성, 생성 결과의 실용성, 유지보수 비용을 기준으로 판단해줘.

## 프로젝트와 첨부 자료

- 검토 기준 버전은 `0.7.20`이다. 개발 도구는 Bun이며, 배포된 CLI는 Node.js 24+와 Bun 1.3+에서 실행한다.
- 저장소에 문서, 에이전트 지침, 계약, 검증 안내, 체크리스트, Mermaid 도표, GitHub 템플릿, 위생 파일, 선택적인 작업 실행기 진입점을 생성하는 TypeScript CLI다.
- 애플리케이션 소스, 웹 앱, 서비스, 데이터베이스, 실행 인프라를 생성하는 제품으로 확장하려는 요청은 아니다.
- 주요 명령은 `init`, `adopt`, `update`, `upgrade`, `doctor`, `eject runner`다. 지원하는 생성 실행기는 `none`, `make`, `just`, `task`, `npm`, `pnpm`이다. CLI를 Bun으로 실행하는 것과 `--runner bun` 지원은 구분해줘.
- 압축에는 소스, 테스트와 fixture, 문서, 패키지·TypeScript·Vitest 설정, CI·릴리스 설정, `bun.lock`이 포함된다. `.git`, `node_modules`, 빌드 결과, 캐시, 로그, 로컬 환경 파일은 제외했다.
- 준비 시점의 Windows 검증은 `bun run check` 성공, 테스트 261개 성공·POSIX 권한 테스트 1개 제외, Node·Bun 실행 및 패키지 설치 검증 성공이었다. 이것을 Linux 검증이나 모든 경쟁 조건의 안전성 증거로 취급하지 마.
- `AGENTS.md`, `README.md`, `SECURITY.md`, `package.json`을 읽고 실제 코드와 비교해줘. 이번 요청은 검토와 개선 제안이며, 커밋·푸시·배포를 실행하라는 요청은 아니다.

## 답해줬으면 하는 질문

1. **지금 출시하거나 실제 저장소에 적용했을 때 가장 먼저 문제가 될 부분은 어디인가?**
   사용자 파일 손실, 잘못된 성공 보고, 소유권 오판, 반복 실행의 불일치, 복구 실패를 먼저 살펴봐줘. 단순히 코드가 마음에 들지 않는다는 이유로 결함이라고 하지 마.

2. **명령과 파일 소유권의 상태 변화가 일관적인가?**
   `init → 사용자 수정 → update → upgrade → eject → update` 같은 흐름을 추적해줘. seeded/managed/block-managed/project-owned, optional/required, active/retired가 사용자 기대와 맞는지 확인해줘. 파일·스크립트 삭제와 재생성, 실행기 변경, `--force`, `--dry-run`, `doctor --strict`, 오래된 manifest 호환성도 포함해줘.

3. **파일 쓰기·롤백·정리·잠금 코드에 여전히 데이터 손실이나 잘못된 파일 접근이 가능한가?**
   검사부터 실제 동작까지의 순서, 심볼릭 링크·junction, 부모 디렉터리와 임시 파일 교체, hard link, 파일 식별 정보, 권한 보존, 잠금 소유권·stale 판단, SIGINT/SIGTERM, 병렬 배치 실패를 확인해줘. 정상적인 다른 프로세스의 수정과 악의적인 디렉터리 교체를 구분하고, 공격자가 필요한 권한도 밝혀줘. 경로 검사나 device/inode 비교만으로 경쟁 조건이 완전히 사라졌다고 판단하지 마. 일반 사용자용 CLI에 필요한 보장과 별도 권한 모델이 필요한 보장을 구분해줘.

4. **생성된 문서와 검증 안내가 실제로 개발에 도움이 되는가?**
   템플릿 함수가 내보내는 결과를 기준으로 검토해줘. 안내의 중복·모순, 존재하지 않는 경로나 명령, 과도한 문서량, 에이전트에게 잘못된 권한을 주는 표현, 제대로 설정하지 않았는데 검증이 성공한 것처럼 보이는 경로가 있는지 확인해줘. 템플릿의 문자열과 CLI 자체의 실행 코드를 혼동하지 마.

5. **사용자가 CLI에서 실패 원인을 이해하고 해결할 수 있는가?**
   JSON·사람용 출력, 종료 코드, 옵션 검증, 비대화형 실행, 부분 실패와 복구 미완료의 표시를 확인해줘. 내부 오류는 보존하되 호출자가 실제로 받는 메시지에서 중요한 원인이 사라지는지도 살펴봐줘.

6. **구조를 단순화해 기능 추가와 수정 비용을 줄일 수 있는가?**
   중복된 상태 판단, 명령별로 다른 저장 경로, 큰 함수와 파일, 불필요한 추상화, 테스트가 구현 세부사항에 묶인 부분을 찾아줘. 파일이 40KB를 넘으면 리팩토링 후보로 볼 수 있지만 크기만으로 분리를 권하지 마. 기존 구조 유지, 작은 수정, 구조 변경의 비용과 이점을 비교해줘. 지금 출시를 늦추면서까지 할 필요 없는 개선은 따로 표시해줘.

7. **성능·배포·CI에서 비용 대비 효과가 큰 개선이 있는가?**
   파일 읽기·쓰기와 메모리 사용, manifest 크기 제한, 패키지 내용, 설치된 실행 파일의 동작, Node/Bun 호환성, Windows/Linux 차이, 릴리스 재실행과 CI 비용을 확인해줘. 측정하지 않은 속도 개선을 단정하지 마. 의존성을 영구적으로 특정 패치 버전에 고정하는 해법보다 같은 메이저의 안정 업데이트를 수용하고 새로운 메이저를 검증해 승격하는 방식을 우선 고려해줘.

8. **현재 테스트가 놓친 중요한 동작과 정리할 수 있는 테스트는 무엇인가?**
   앞에서 확인한 결함을 재현하는 작은 테스트를 우선 제안해줘. 구현을 그대로 흉내 내는 테스트, 오래된 가정, 중복 검증, 실제 플랫폼 차이를 감추는 mock도 확인해줘. 검증량을 무작정 늘리거나 모든 변경에 새 CI 작업을 추가하지 마.

## 답변 형식과 근거 기준

먼저 출시를 막을 정도의 문제가 확인됐는지, 그리고 가장 먼저 고칠 항목이 무엇인지 짧게 답해줘. 다음으로 영향이 큰 개선을 최대 5개까지 우선순위순으로 설명해줘. 근거 있는 항목이 적으면 적게 제시해도 된다.

각 항목에는 다음 내용을 포함해줘.

- 확인된 결함 / 재현 전 가설 / 설계 개선 제안 중 어느 것인지.
- 관련 파일과 실제 줄 번호, 해당 함수와 호출 경로.
- 발생 조건, 필요한 플랫폼·권한·동시 동작, 기대 동작과 실제 동작.
- 사용자가 겪는 영향과 우선순위를 그렇게 정한 이유.
- 재현 방법 또는 작은 회귀 테스트. 실제 실행 여부와 결과를 명시해줘.
- 가장 작은 수정안과, 필요하다면 더 단순한 구조 대안. 예시 패치나 의사 코드는 해당 위치와 연결해줘.
- 호환성·회귀 위험, 꼭 필요한 검증, 독립적으로 커밋할 수 있는 작업 범위.

마지막에는 먼저 처리할 최대 3개의 작업을 순서대로 적고, 이번에 손대지 않는 편이 나은 영역과 판단에 필요한 미확인 정보를 짧게 적어줘.

압축 파일을 실제로 열어 코드를 읽지 못했다면 그 사실부터 알려줘. 파일이나 줄 번호, 실행 결과를 만들어내지 마. 실행 환경이 없으면 정적 분석 결과라고 명시하고 검증했다고 쓰지 마. Windows 전용 조건과 POSIX 전용 조건을 구분해줘. 플랫폼·런타임·패키지 매니저의 세부 동작이 불확실하면 공식 문서로 확인하거나 미확인이라고 표시해줘.

이미 README에서 명시한 제약은 새로운 결함처럼 반복하지 말고, 그 제약 때문에 실제 사용에서 문제가 생기는 구체적인 조건과 현실적인 해결책을 제시해줘. 이전 수정이 잘됐을 것이라고 가정하지 말고 현재 코드로 판단해줘. 보기 좋은 일반론보다 근거 있는 지적과 바로 실행할 수 있는 개선안을 원한다.
